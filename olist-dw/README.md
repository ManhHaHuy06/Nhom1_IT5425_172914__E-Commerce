# Olist MySQL Data Warehouse Loader

This project loads Spark CURATED Parquet data from MinIO into MySQL 8.0.

## Architecture

Olist API -> Crawler -> MinIO RAW -> Spark ETL -> MinIO CURATED -> DW Loader -> MySQL DW

## Curated datasets expected

- dim_geolocation
- dim_category
- dim_customer
- dim_seller
- dim_product
- dim_date
- fact_orders
- fact_order_items
- fact_payments
- fact_reviews
- fact_customer_order

## Requirements

- Docker Desktop
- MinIO already running at host.docker.internal:9000
- Bucket: olist
- Spark ETL must have completed successfully and created `curated/`
- Docker Compose

## Important

The MySQL database is exposed on host port 3307 to avoid conflict with an existing MySQL on port 3306.

MySQL credentials:
- database: olist_dw
- user: olist
- password: olist123
- root password: root

## First run

From this directory:

```powershell
docker compose up -d mysql-dw
docker compose ps
docker compose run --rm dw-loader
```

The MySQL schema is automatically initialized on first creation of the volume.

## Reload after another Spark ETL run

The default is:

```text
LOAD_MODE=replace
```

so the loader clears the DW tables in dependency order and reloads all curated Parquet.

```powershell
docker compose run --rm dw-loader
```

## Access MySQL

From Windows:

```powershell
mysql -h 127.0.0.1 -P 3307 -u olist -p
```

Password:

```text
olist123
```

Or:

```powershell
docker exec -it olist-mysql-dw mysql -uolist -polist123 olist_dw
```

## Notes

RAW and CURATED remain in MinIO. The loader does not modify or delete them.

The schema follows the current Spark ETL outputs rather than loading the original Olist CSV files directly.


## Important BIGINT handling

Spark `LongType` is a signed 64-bit integer. Several surrogate keys generated by
`xxhash64()` can be larger than the exact-integer range that a floating-point
`float64` can represent.

The loader therefore explicitly converts all DW key columns to pandas nullable
`Int64` before building MySQL insert parameters. This prevents precision loss
such as:

```text
-6977141296617389362
```

being converted to an approximate floating-point value.

Do not remove this conversion.
